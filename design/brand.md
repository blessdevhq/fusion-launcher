# Brand contract — Fusion Launcher

## Audience and moment

A Windows retro-game owner is building or operating a personal library. They need to connect a permitted source, understand setup requirements, install or launch safely, and recover from errors without becoming an emulator expert.

## Visual thesis

Make a technical launcher feel like a cinematic personal game library with a calm,
trustworthy operating layer — capable and modern, not militaristic, arcade-themed
or storefront-like.

## Deliberate visual moves

- Use layered near-black surfaces to establish a focused desktop workspace around real game artwork.
- Use Fusion green for readiness, progress, selected focus and primary completion; preserve it as a signal rather than a decoration.
- Keep the shell, title bar, sidebar and controller hints structurally quiet so the current task and game content remain legible.
- Prefer explicit operational status, source provenance and setup progress over speculative marketing language.
- In browseable library states, make the selected game a cinematic focal point and use a
  compact cover rail to express the larger collection. The user should understand both
  “what is selected” and “what else is available” at a glance.
- Create depth with an artwork plane, a controlled contrast scrim and a foreground action
  plane—not with generic translucent cards, ubiquitous blur or green glow.
- Keep a strict mode shift: expressive authorised game art belongs to selection and
  discovery; safe installation, diagnostics and recovery stay calm, opaque and factual.

## Anti-references

- No generic SaaS dashboard card grid for core navigation; the launcher has task-specific shell panels and stateful game operations.
- No all-purpose neon, glassmorphism or animated background treatment; it weakens status hierarchy and Windows desktop clarity.
- No copied game-store assets, logos, screenshots, copy or CSS. External artwork remains subject to the product's source and legal model.
- No imitation of the supplied references' identifiable console, streaming or storefront
  trade dress. Borrow only abstract hierarchy and interaction principles.
- No hero image that conceals a source warning, setup requirement, install state or
  keyboard/controller focus treatment.
- No synthetic “AI magic” layer: floating 3D ornaments, aurora gradients, decorative
  particles, generic promise copy, vanity KPIs or fake activity dashboards are not a
  substitute for a game, live launcher state or next safe action.
- No visual equality by repetition: avoid giving every section a glowing rounded card,
  icon badge, metric and call-to-action. Hierarchy comes from the user's task, not from
  component count.

## Signature motif

A cinematic game stage inside a dark desktop cockpit: stable shell framing, one
currently selected title, restrained green readiness signals, and authentic game art
as the user's library content rather than as generic background decoration.

## Content and imagery direction

- **Image/illustration policy:** Prefer user-provided or source-authorized cover/hero artwork; retain clear fallbacks for missing imagery.
- **Icon policy:** Use the existing Lucide icon language for operational controls; do not introduce mixed icon sets without a reason.
- **Copy tone:** Direct, calm, factual and permission-aware. State setup requirements and errors plainly.
- **Motion policy:** Motion indicates progress, arrival, selection or state change; it never delays a launch/setup decision.
- **Ornament policy:** Every visual object must earn its space through authorised game
  content, live data, an explicit state, navigation or an actionable control. Remove
  decorative UI whose purpose cannot be named.

## Approval boundary

Human approval is required before changing this contract, shared visual roles, canonical shell primitives or visual baselines.
