# Fusion Creator v1: план параллельной реализации

Исправленная разбивка согласованного Creator v1 на независимые потоки. План рассчитан на четыре одновременно активных агента: интегратор и не более трёх исполнителей. Буквы обозначают ответственность, а не обязательное число отдельных агентов; одного исполнителя можно последовательно назначать на несколько потоков.

## Результат и границы v1

Автор создаёт проект из установленной игры или portable-сборки, проверяет состав и происхождение, задаёт профили, собирает Source, восстанавливает его обычным установщиком в отдельной директории и экспортирует выпуск. Игрок устанавливает, обновляет и откатывает сборку через Launcher.

- Общая модель Creator; первый встроенный адаптер — portable Eden 0.2.1. TOTK — частный пример, а полный игровой QA и измеренные FPS-пресеты не блокируют общий Creator.
- Управление: клавиатура/мышь и один SDL GameController. Выбор устройства, назначение и проверка кнопок полностью внутри Fusion. Dual Joy-Con и специальные игровые подсказки вне v1.
- Публикация: подписанный экспорт и проверка размещённого HTTPS Source. Автор загружает файлы на хостинг самостоятельно.
- Переиспользуются существующие Packer, FusionService, CAS, snapshots, supervisor, подписи и TOFU. Обязательная регистрация, ИИ, маркетплейс, ротация и отзыв ключей в этот выпуск не добавляются.

## Перед стартом: интегратор

- Снять состояние текущей ветки и незакоммиченных изменений. Не сбрасывать и не смешивать посторонние изменения с Creator. Для работы в отдельных worktree сначала подготовить согласованный Git-снимок необходимых текущих изменений: worktree от прежнего HEAD их не наследует. Не запускать исполнителей на устаревшей базе.
- Назначить владельцев модулей и общих файлов, зафиксировать зависимости и критерии приёмки. Каждый исполнитель знает, что работает не один, и не отменяет чужие изменения.
- Модель доверия уже выбрана: существующая подпись Ed25519 и TOFU с сохранением пина ключа. Смена или удаление ключа не принимаются незаметно. Доверие источнику не заменяет approval конкретного исполняемого файла.
- При несовпадении хеша остановить обработку входа до изменения активной установки. Показать компонент, ожидаемый и фактический хеш и действия «Выбрать другой файл» / «Повторить загрузку». Продолжения с неверным хешем нет; изменённый бинарник требует собственного approval.
- Не назначать календарные сроки по числу экранов. Сначала подтвердить техническую базу и Windows-сборку SDL.

## Волна 0: база, контракты и общий тестовый харнесс

**Владелец: интегратор.** Эта волна предшествует параллельной реализации.

1. Воспроизвести lifecycle-тест вне ограничений sandbox. Зафиксированная ошибка `Access denied` на hard link не доказывает кросс-томную причину. Если ошибка повторяется, диагностировать конкретную файловую операцию и исправить её с регрессионным тестом. Копирование между томами проверять отдельно в рамках существующей политики проекции; не заменять им отказ в доступе без диагностики.
2. Зафиксировать Rust/TypeScript-контракты: `GameManifest 1.1`, `CreatorProject`, происхождение компонентов, профили сборки/управления, ссылка на встроенный адаптер, правила `path → winningLayer`, Creator job/report DTO и input DTO. `SourceIndex` остаётся 1.0; новый клиент принимает manifests 1.0 и 1.1.
3. Определить минимальные интерфейсы нормализации, подготовки candidate и устройства ввода. Resolver — общий чистый модуль; отдельный трейт для него или для уже существующей подписи не вводить без реальной необходимости.
4. Зафиксировать IPC и события `fusion-creator:job-progress` / `fusion-input:state`, правила `jobId` или `sessionId` и `sequence`. Моки доступны только через preview/test bridge. Не включать в production команды, сообщающие фиктивный успех; незавершённые действия недоступны либо возвращают явную ошибку недоступности.
5. Поручить C единую миграцию реестра проектов, приватных привязок, заданий, выпусков и отчётов. Номер — следующий свободный после актуальной схемы; сейчас исходная база имеет версию 5. G использует этот storage API, отдельную конкурирующую миграцию не создаёт.
6. Зафиксировать границы возобновления: сохранённый результат сканирования/классификации; каждый полностью проверенный и атомарно сохранённый артефакт; собранный неизменяемый выпуск; завершённая проверка; завершённый экспорт. Перед повторным использованием сверять ревизию проекта, хеши входов и версии адаптера. Незавершённый файл или частичная операция не считаются checkpoint.
7. Подготовить основу H: собственный синтетический fixture, изолированные SQLite/library/workspace, полный `InstallRequest` и обычный desktop transport. Расширять имеющиеся тестовые helpers, не строить второй установщик. Проверка через полностью offline transport не заменяет получение внешних HTTPS-зависимостей.
8. Зафиксировать единый набор fixtures для UI и namespace ключей в существующей i18n. Пустые отдельные файлы локализации ради потоков не нужны.

**Готово, когда:** согласованные контракты компилируются, существующий lifecycle-сценарий подтверждён или его воспроизводимая ошибка исправлена, общий харнесс доступен всем потокам. Новое поведение пока не рекламируется пользователю как работающее.

## Волна 1: A, B, C параллельно

### A. Packer, манифест и переносимые ссылки

- **Владеет:** Packer, wire/canonical-модели, parsing, наследование и разрешение URL при получении слоёв. Общие изменения wire-модели других потоков проходят через A.
- **Делает:** поддержку manifest 1.0/1.1 во всех точках проверки; наследование 1.1 от 1.0/1.1 и запрет 1.0 от 1.1; required capabilities; режимы рецепта `managed`, `external`, `user_provided`.
- Reference-файлы инспектируются приватно. В managed-экспорт попадают только явно разрешённые артефакты; external содержит закреплённые HTTPS-ссылки, user_provided — локальные требования. Подготовка пользовательских директорий использует одну детерминированную нормализацию у автора и игрока через согласованный с B helper.
- Добавляет относительные URL от корня Source, сохраняя исходный Source у наследуемых слоёв. Байты манифеста и подпись не меняются при переносе с локальной папки на HTTPS. Абсолютные внешние HTTPS-ссылки сохраняют свой смысл.
- Отличает external inventories от пропавших managed-артефактов. Подключает общий resolver B и проверяет каждый допустимый профиль отдельно.
- **Готово, когда:** старые рецепты сохраняют выпуск 1.0; старый клиент блокирует 1.1 с `UnsupportedSchema`; reference payload/пути не попадают в экспорт; относительные ссылки и наследование покрыты тестами. Полная приёмка A требует подключения B, а не временной production-заглушки.

### B. Установщик, профили и resolver

- **Владеет:** план установки, GameOptions, snapshots, подготовка candidate, integrity/executable approval и общий resolver файловой проекции.
- **Делает:** `buildProfileId` и `controlsProfileId`, допустимые сочетания и конечные наборы дополнений; staging выбора и применение через `game_update`. Произвольное смешивание дополнений с конечным профилем в v1 отклоняется.
- Resolver принимает выбранные слои, проверенные inventories и явные правила победителя. Одинаковый путь/хеш допустим; разные хеши требуют решения автора. Зависимости не задают неявный приоритет. Для Source 1.0 сохраняется прежняя семантика.
- Проверяет проекцию до создания candidate. Ожидания integrity и approval рассчитываются по реально выбранному provider бинарника. Патчи и шаблоны сохраняют отдельные проверки входов/выходов.
- Добавляет точку подготовки неактивной генерации для D. Она не изменяет shared persistence или конфиг активной версии до переключения. Обрабатывает user_provided входы и использует общую нормализацию директорий A.
- **Готово, когда:** Packer и installer используют один resolver; неверный профиль/конфликт блокируется до изменения установки; ошибка, отмена и rollback сохраняют рабочую генерацию и saves.

### C. Backend Creator и хранение

- **Владеет:** проектный модуль, отдельные Creator DTO/IPC, storage, jobs и реестр выпусков/проверок.
- **Делает:** атомарное сохранение переносимого проекта, отдельные приватные bindings, миграцию SQLite, версионирование `CreatorProject`, фиксацию ревизии для задания, один writer на workspace, progress/cancel/recovery.
- После перезапуска незавершённое задание становится `interrupted`; продолжение повторно проверяет checkpoint. Синхронный Packer вызывается как библиотека в blocking worker с контрольными точками отмены и прогресса.
- Закрытие UI не отменяет job. Поздние события не возвращают завершённое задание в running. Изменение проекта делает текущий статус проверки устаревшим, сохраняя историю прежних неизменяемых выпусков.
- **Готово, когда:** реальные операции сохраняются и восстанавливаются; прерывание не повреждает прошлый выпуск; устаревшие результаты не применяются к новой ревизии.

## Волна 2: D, E, F параллельно

Начинается после интеграции A/B/C. Договорённые интерфейсы позволяют D работать с тестовым input provider, а E — с fixtures сериализации без ожидания игрового запуска.

### D. Адаптер Eden

- **Владеет:** встроенный `eden_portable`, сканирование/нормализация Eden, владение конфигурацией и Eden-сериализация управления.
- **Делает:** проверку идентичности runtime 0.2.1; импорт поддерживаемых глобальных/game-specific настроек, input profiles и модов. Версия игры не определяется по имени папки.
- Использует allowlist переносимых настроек. Saves, ключи, firmware, журналы, кеши, учётные данные, история и персональные пути исключаются из managed-экспорта; обязательные игровые/системные файлы оформляются локальными требованиями. Неизвестные настройки показываются как неперенесённые.
- Для новых Sources разделяет saves, локальные предпочтения и конфиги генераций; не сохраняет весь `runtime/user` как persistent. Применяет профиль в candidate через B, сохраняя локальные bindings при обновлении/откате. Старый whole-user hook остаётся для существующих установок.
- Только D преобразует структурированные назначения в валидированный Eden `ParamPackage`. Логическое управление переносимо, физические GUID/port/калибровка остаются у игрока.
- **Готово, когда:** подготовка не меняет активную установку, перенос учитывает game-specific конфиги, обновление/откат сохраняют пользовательское состояние, а неизвестный runtime/настройка объясняются явно.

### E. SDL-сервис внутри Fusion

- **Владеет:** отдельный модуль input service в существующем Rust-приложении. Выделение crate не является требованием v1. Изменения Cargo-зависимостей передаются интегратору.
- **Делает:** `sdl2 0.38.0` с `bundled`/`static-link`; один worker владеет SDL context и handles; обнаружение устройств, проверку кнопок/осей, назначение и калибровку внутри Fusion; ограниченное по частоте событие input state.
- Возвращает логические SDL inputs, raw bindings и приватную идентичность для D. Session instance ID не переносится в Eden. Нормализация GUID и SDL hints согласуются с закреплённым драйвером Eden; неизвестная раскладка не угадывается по номеру кнопки.
- Перед запуском Eden закрывает handles и подтверждает освобождение устройств. Если подтверждение не получено, запуск останавливается с диагностикой; таймаут сам по себе не доказывает закрытие handle. Переподключение и неоднозначные одинаковые устройства требуют повторного разрешения локальной привязки.
- **Готово, когда:** Windows-сборка и fixtures кнопок, hats, sticks, triggers, disconnect/reconnect и остановки проходят. Это завершение автоматической части E; для приёмки всего v1 остаётся физический smoke.

### F. Интерфейс Creator и управления

- **Владеет:** экран Creator, проектный/input store, frontend API-обёртки, i18n и соответствующие preview fixtures.
- **Делает:** список проектов, этапы «Основа → Состав → Профили → Проверка → Выпуск», историю, диагностику, возобновление jobs и экран выбора/проверки устройства.
- Работает с реальным IPC C; недостающие сценарии D/E/G разрабатывает в preview/test bridge с теми же DTO. Preview не сообщает о реальной записи файлов или публикации.
- Владеет захватом ввода и focus scope: назначаемые клавиши не активируют shell; вложенный диалог ограничивает навигацию своим корнем. Добавляет русский/английский текст и использует существующие визуальные роли.
- **Готово, когда:** frontend проверки и четыре viewport проходят, реальные C-операции работают, а ожидающие D/E/G действия явно отделены от доступных. Успешные моки не завершают приёмку продукта.

## Волна 3: G, F2, H2 параллельно

### G. Подпись, экспорт и проверка

- **Зависит от:** A/B/C/D; использует готовый input API E для выбранных control profiles.
- **Владеет:** компиляция проекта в рецепт, задания build/verify/export, сравнение выпусков, экспорт по allowlist и проверка HTTPS. C остаётся владельцем job runner/storage, G реализует обработчики через его API.
- Переиспользует Ed25519, локальное защищённое хранение ключа и TOFU; не добавляет отдельный SigningProvider, ротацию, отзыв или модель официального автора.
- Выполняет чистую установку через обычный FusionService с отдельными SQLite/library/workspace и полным `InstallRequest`. Исходная папка автора недоступна; пользовательские требования передаются отдельно.
- Разделяет отчёты структуры/целостности, чистой установки, наблюдаемого запуска, ручного сценария и HTTPS acquisition. Отчёт связан с выпуском, адаптером, профилями и средой.
- Экспорт допускается после структуры и чистой установки всех заявленных сочетаний профилей. После ручного размещения HTTPS-проверка выполняет полное streaming-получение обязательных загрузок с пустым кешем, а не только HEAD. Подпись не выдаёт executable approval.
- **Готово, когда:** локальная и HTTPS-установка используют одинаковые байты/хеши; external действительно получены и проверены; экспорт не содержит приватных файлов/путей, ключа подписи и device IDs.

### F2. Завершение интеграции UI

- **Владелец:** тот же поток F; зависит от C/D/E и поэтапно подключает реальные G-операции.
- Подключает выбор профилей у игрока, назначения и калибровку устройства, build/verify/export, отмену и повторное открытие задания. Убирает временную недоступность реализованных действий; preview fixtures остаются только для preview/tests.
- Отдельно показывает «ввод проверен», «процесс запущен», «игровой сценарий проверен» и «HTTPS получение проверено». Не объединяет их в безусловное «проверено».
- **Готово, когда:** основной пользовательский путь работает с production IPC; ошибка любого этапа имеет понятное восстановление.

### H2. Расширение общего харнесса

- **Владеет:** общие integration/native fixtures и тестовый harness. Тесты модулей пишут владельцы A–G; H2 не становится единственным автором всех тестов.
- Расширяет основу H для воспроизводимой сборки, недоступной исходной папки, изоляции пользовательских требований, конфликтов, смены профиля, обновления/отката, отмены и crash recovery.
- Проверяет относительные URL и inherited origins, external с пустым кешем, подпись/пин, неверные хеши и отсутствие приватных данных в экспорте.
- Для политики разных томов использует детерминированный тест выбора стратегии и отдельную Windows-проверку на реальных томах при их наличии. Отсутствие второго тома отмечает как NOT TESTED, а не как PASS.
- Добавляет native UI-сценарий полного цикла в существующий Windows harness. Тестовые helpers не становятся production backdoor.
- **Готово, когда:** общий сценарий использует реальные A–G, а результаты отделяют автоматические проверки от аппаратных и ручных.

## Волна 4: финальная интеграция и приёмка

**Владелец: интегратор.**

- Полный цикл в native UI: импорт/создание проекта → профили → сборка → чистая установка → изменение конфига/версии → обновление → rollback → повторное открытие проекта и истории.
- Физический smoke хотя бы на одном SDL-геймпаде: выбор и назначения в Fusion, проверка сигналов, освобождение устройства перед Eden, применение профиля и повторное обнаружение. Fixtures не заменяют этот результат.
- TOTK используется только локально на пользовательских файлах. Отсутствие полного TOTK gameplay QA или замеров FPS не блокирует общий v1; непроведённые сценарии обозначаются NOT TESTED.
- Прогнать `npm run qa` и `npm run mvp:visual`; проверить 1280×720, 1365×768, 1440×900 и 1920×1080, обе локализации, focus/capture, длинные пути, ошибки, прокрутку и доступность основных действий.
- Обновить спецификацию Source, руководство Packer и инструкцию Creator. Описать intended visual diffs; не утверждать новые общие роли или screenshot baselines автоматически.
- Выпуск v1 принимается только после реального общего сценария и физической проверки выбранной поддержки управления. Наличие интерфейсов, компиляция или моки сами по себе не означают готовность.

## Владение общими файлами и порядок интеграции

| Область | Владелец и правило |
| --- | --- |
| Wire/canonical-модели и наследование | A; необходимые изменения B/D/G передают A |
| GameOptions, план, snapshots, resolver | B; A/D/G используют согласованный API |
| Creator DTO/IPC, storage и миграция | C; G подключает обработчики, не создаёт параллельный job runner |
| Eden-конфиги и ParamPackage | D; E предоставляет SDL bindings, F — структурированные назначения |
| Native input service | E; SDL handles не передаются в Tauri State или UI |
| Экран Creator, frontend stores/API, i18n | F; остальные передают контракты и ключи |
| Cargo.toml/Cargo.lock, package.json/lock, IPC-регистрация, общая проводка | Интегратор; изменения применяются согласованно, без конкурентной перезаписи |
| Общий integration/native harness | Интегратор в волне 0, затем H2; unit-тесты остаются у владельцев модулей |

Исполнители работают от общего снимка волны 0 в отдельных worktree. Независимые небольшие части интегрируются по мере готовности; не ждать завершения всех потоков для первой совместной проверки. Взаимозависимые изменения A/B принимаются согласованно, затем C; после этого D/E/F и G/F2/H2. После интеграции запускать относящиеся к изменению проверки; полный набор — на межволновых границах и финальной приёмке.

Изменение замороженного контракта проходит через владельца и интегратора, сообщается зависимым потокам и сопровождается обновлением fixtures. Неполное поведение остаётся недоступным пользователю, а не маскируется моками.

## Зависимости и критический путь

Основные цепочки:

- Волна 0 → A/B/C → D → G → F2/H2 → финальная приёмка.
- Волна 0 → E → интеграция D/F2 → физический smoke → финальная приёмка.
- Волна 0 → F → F2 → native UI и visual-приёмка.

A и B взаимозависимы через общий resolver; экспорт зависит от реальной установки B и адаптера D. SDL, UI и харнесс можно разрабатывать параллельно, но их незавершённость блокирует заявленный полный v1. Без длительностей нельзя объявлять одну цепочку единственным календарным критическим путём.

Порядок волн соблюдает лимит интегратор + три исполнителя. Объём управления, проверки или калибровки не сокращается автоматически ради срока; такое изменение требует отдельного решения пользователя.
