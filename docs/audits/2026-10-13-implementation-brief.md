# Fusion Launcher: итоговое задание исполнителю

Дата: 13 октября 2026 года. Базовый HEAD: `2ff0ec4505fe463583678609b0fd8efe061ba727`.

Основные требования двух рецензентов согласованы. Новый большой раунд проектирования не нужен. Наброски из переписки — материал для реализации, а не проверенный код. Этот документ завершает подготовку разбора; исходники приложения не изменялись.

## Исправления к последнему наброску, обязательные при реализации

### 1. Маркер из архива не даёт право удалять папку

Не переносить предложенный hotfix с условием `canon.join(".fusion-owned").is_file() || is_game_dir_in_library(...)` буквально.

- Архив может содержать `.fusion-owned`: простое наличие файла не доказывает создание и исключительное владение папкой со стороны launcher.
- Два компонента пути не доказывают владение. Обычная схема игр — `library_root/Games/platform/subject`, а не два уровня от `library_root`. Отдельный `download_root` и custom destination также поддерживаются.
- Предложенный код сначала каноникализирует путь и затем удаляет результат. Это не сохраняет защиту от junction/symlink и может направить удаление на чужой target. Одной проверки `other_records` также недостаточно.

Минимальный защитный патч: прекратить рекурсивную очистку каталогов с недоказанным владением, включая fallback через `candidates.push(torrent.save_dir)`. Сообщать, что файлы сохранены. Не заменять эту защиту разрешением по маркеру или форме пути. Точные файлы тоже проверяются на владение и ссылочные компоненты пути.

Целевой вариант: отдельная управляемая папка установки, созданная приложением без присвоения уже существующей чужой папки; доверенная запись владельца/установки; отдельный staging. Данные владения не принимаются из скачанного payload. Архив не может перезаписать метаданные владения. Legacy-папки с неизвестным происхождением рекурсивно не очищаются.

Регрессионные тесты: sentinel в custom target; архив с подложенным маркером; существующая чужая папка с именем game ID; junction/symlink в target или предках; одинаковый filename у двух игр; частичная ошибка очистки и повтор. Тесты работают только в temp и не удаляют реальные пользовательские каталоги.

### 2. Таблица переходов должна учитывать действие и runtime

В предложенном `allowed_from("downloading")` разрешён `paused`. Поэтому общий helper с одним параметром `to = downloading` разрешит и старому progress перевести `paused` в `downloading`. Заявление «progress только downloading → downloading» не обеспечено этим наброском.

Разделить полномочия действий: progress обновляет только уже downloading; переходы start/resume принадлежат управляющему коду, с проверкой текущей runtime-generation. Одного `attempt_id` недостаточно, если resume сохраняет тот же attempt, но запускает новый worker. Проверять generation во всех runtime callbacks либо назначать новое поколение операции на каждый runtime-старт, сохраняя отдельную логическую идентичность установки.

Тесты: поздний progress после pause не снимает паузу; callback старой runtime-сессии после resume не меняет новую; A → delete → B защищён для progress/status/handle/completed/error/assets и IPC.

### 3. Окончание lease не тождественно окончанию sidecar

Модель `OpLease(Arc<Inner>)` пригодна при условии, что каждый writer и каждый блокирующий worker удерживает собственный lease. Снятие owner из карты не доказывает остановку внешнего процесса.

В `LibtorrentEngine` уже есть generation и обработка `CommandEvent::Terminated`. Использовать отдельное подтверждение завершения именно нужного процесса; `child.take()`, успешный kill и фиксированная задержка не заменяют его. При закрытии event stream без подтверждения не начинать destructive cleanup. Учесть ветки, где процесс уже создан, но ещё не помещён в entry: они сейчас вызывают kill без запуска обычного event loop.

Самый ранний момент разрешённой очистки — после stop backend и завершения всех writers, включая spawn/add, polling, события процесса, hashing и extraction. Истечение таймаута не снимает защиту от параллельного старта активной операции.

### 4. Разногласие о fastresume разрешить консервативно

Первый рецензент предлагает удалять fastresume при любом удалении записи; второй требует отдельного основания для удаления данных восстановления. Для итогового задания выбрано правило: **при `delete_files=false` сохранять payload и fastresume**. Удаляется управление в приложении; повторное добавление может использовать сохранённые данные. Пауза также сохраняет файлы. При `delete_files=true` очищаются только доказанно принадлежащие установке payload и служебные файлы.

Это требование к будущему патчу, а не описание текущего поведения: сейчас `engine.delete(id, false)` всё равно удаляет fastresume. Результат очистки должен различать Deleted, Absent и Preserved(reason); нельзя сообщать полное удаление на `PolicyRefused`.

## Патч A: lifecycle и файловое владение

1. Защитный запрет опасной рекурсивной очистки и sentinel-тест. Не подключать недоделанный новый orchestration-путь.
2. Coordinator, lease и резервирование удаления до побочных эффектов; уникальный attempt; разделение логической попытки и runtime. Нет std/SQLite mutex через await.
3. HTTP headers/body/DNS отменяются; hashing/extraction кооперативны и учитываются до выхода worker. Обрыв/stall сохраняет пригодный partial, явное удаление очищает только свои артефакты.
4. Условные worker-записи по attempt/runtime/разрешённому действию; завершение первой установки по-прежнему создаёт downloads. Assets и связанные записи защищаются внутри той же транзакции.
5. Legacy `download_game` обращается к общей реализации; queued/resume/restore не обходят coordinator. Миграция с текущего user_version 2 атомарна; legacy NULL получает корректный attempt до старта worker.
6. Недеструктивный stop sidecar и подтверждённое quiescence; очередь продвигается после освобождения слота; остановка не зависит от ожидаемого до неё guard.
7. Управляемые папки/staging, проверка владения, повторяемая очистка; безопасное сохранение неизвестных legacy-файлов. SQLite не обещает откат уже удалённых файлов.
8. IPC attempt/runtime и игнорирование погашенных поколений. Metadata artwork допускается восстановить как кэш после удаления; не заявлять, что кэш останется пустым.

Минимальные release-blocking сценарии: A→delete→B с поздними callbacks; active/queued/paused torrent; сохранение файлов при false; зависшие headers/body; удаление при blocking hashing/extraction; stop timeout без cleanup; первая установка/retry/assets/legacy; migration/restart; sentinel/подложенный marker/junction/коллизия путей; очередь после отмены; запоздалые IPC.

## Патч B: network/trust

Ручные ограниченные редиректы с проверкой каждого URL и `Url::join`; HTTPS не понижается. В прямом режиме проверяются DNS-адреса и использование именно их, без fallback на непроверенное разрешение и без подмены TLS hostname на IP. Реальная конфигурация клиента определяет режим, а не только подпись в настройках.

Proxy-compatible режим сохраняет системный прокси и Fake-IP; прокси считается доверенным сетевым посредником. Контроль конечного IP за произвольным прокси не обещается. Для внешних источников URL с userinfo отклоняются; cross-origin credentials не пересылаются. Лимиты времени, редиректов и реально прочитанных байтов действуют для JSON и artwork, включая chunked. Специализированные API сохраняют отдельные политики.

Общий effective trust для preview/storage на существующих official/community/unknown. Не добавлять untrusted и не доверять объявленному внешним JSON official.

Тесты: HTTPS→HTTP, private/loopback/link-local/mapped IPv6, запрещённый DNS на следующем hop, разрешённый относительный переход, цикл/лимит/плохой Location, chunked oversized JSON/image, credentials/userinfo, trust parity, proxy/Fake-IP. Production-политика не ослабляется ради локального fixture.

## Проверки и границы задания

Каждый coherent-коммит компилируется и проходит относящиеся к нему тесты, fmt и Clippy. После объединения — полный QA, реальные Rust/Tauri-сценарии и backend-review на одном SHA. Выводы проверок прикладываются фактически; inventory тестов и preview smoke не заменяют прогон backend.

Не включать массовую декомпозицию UI, новые платформы/AI-функции, генерацию типов или публикацию релиза. При неизбежных изменениях уведомлений соблюдать Visual OS и проверить покрытые состояния.

Запрошенные первым рецензентом `TorrentEngine`, add/pause/resume, sidecar event loop и очередь приложены отдельным файлом `2026-10-13-torrent-runtime-evidence.md`. Это точные выдержки текущего дерева, не исправления. Дальнейшие вопросы проверяются на коде и тестах при реализации, а не отдельным большим теоретическим раундом.
